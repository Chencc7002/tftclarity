# Web 上线容量测试计划：2 核 2GB / 100 人在线

> 项目：tftclarity / TFTAgent
>
> 目标环境：单台 2 vCPU、2GB 内存、50GB 系统盘、30 Mbps 公网带宽
>
> 目标负载：峰值同时在线 100 人，AI 全站每日最多 50 次
>
> 更新日期：2026-08-06

## 1. 结论

当前阶段 0～4 的代码、自动化测试和本地 PostgreSQL/Redis 容器验收已经完成，具备进行生产容量测试的前提。刚完成的完整回归结果为：

```text
测试总数：633
通过：619
跳过：14
失败：0
```

但“架构完成”不等于“当前服务器已经证明可以承载 100 人在线”。正式判断需要在截图对应的服务器部署新拓扑后执行本文测试。

基于现有信息的预判：

- 100 人在线、每人有正常阅读和输入间隔时，API 平均负载预计是个位数到低两位数 RPS，这台服务器有通过测试的可能。
- AI 全站每日 50 次对总吞吐压力很小，主要影响 Worker 排队时间和第三方模型费用，不应成为 Web 请求瓶颈。
- 2GB 内存是最紧张的资源。PostgreSQL、Redis、Web、Worker 和 Caddy 同机运行时必须实测内存峰值。
- 30 Mbps 足以承担普通 JSON API；背景图优化后仍需验证 100 个新访客同时冷启动的体验。
- 2026-08-06 已把默认背景从约 2.49MB 的 PNG 切换为约 374KB 的高质量 WebP，把亚索背景从约 1.77MB 降到约 206KB；原图保留为母版，不再由目录默认引用。
- 四张壁纸选择器缩略图合计约 90KB，并且只在打开移动端选择器时加载。壁纸响应已增加一年期 `immutable` 缓存和内容版本文件名/查询参数。

因此当前结论是“**有条件进入压测**”，不能在压测前直接写成“支持 100 人并发”。

## 5. 测试负载模型

“100 人同时在线”不等于“100 个请求每秒”。本计划使用更接近产品行为的模型：

### 正常在线模型

```text
虚拟用户：100
持续时间：15 分钟起，最终稳定性测试 2 小时
用户思考时间：15～30 秒
预期平均 API 速率：约 3～7 RPS
短时目标峰值：20 RPS
```

行为比例建议：

| 行为 | 比例 |
| --- | ---: |
| 浏览首页和运行状态 | 20% |
| 热门阵容/趋势查询 | 30% |
| 英雄装备查询 | 30% |
| 多轮追问和偏好读取 | 15% |
| 反馈提交 | 5% |

AI 任务不按普通请求比例随机触发，单独测试，避免一次压测耗尽真实模型日额度。

### 突发模型

```text
100 个客户端在 10 秒内发起一次缓存命中查询
随后恢复到 3～7 RPS
```

这用于模拟分享链接、群聊传播或版本更新后短时集中访问，不代表持续 100 RPS。

### 压测执行位置与限流隔离

- 负载发生器必须运行在另一台电脑或临时压测主机上，不能运行在被测 2 核 2GB 服务器中，否则 CPU、内存和网络结果失真。
- 当前普通请求限制是每 IP 每分钟 30 次。单台压测机模拟 100 个访客时会先收到大量预期内的 429，无法测出服务器容量。
- 容量测试应在受访问控制的临时测试环境中提高该限制；测试完成后恢复生产值。限流正确性仍使用生产值单独测试。
- 不允许通过公网伪造 `X-Forwarded-For` 绕过限制。若需模拟多个来源 IP，应使用受控的分布式负载发生器或只对测试环境开放的可信代理。
- 需要增加“多人共享同一 NAT 出口”的产品测试。当前仅按 IP 的 30 次/分钟限制可能误伤学校、公司、网吧等共享网络用户；这属于限流策略问题，不属于服务器容量不足。

## 6. 测试前置门槛

以下任一项失败时，不开始公开压测：

- `docker compose ps` 中 PostgreSQL、Redis 和 Web 不是 healthy/running。
- `/api/ready` 不是 HTTP 200。
- `npm run db:status` 显示存在待执行迁移。
- 生产环境仍允许 Memory fallback。
- PostgreSQL 或 Redis 端口发布到公网。
- 服务器可用磁盘低于 15GB。
- 未完成旧业务库备份和迁移校验。
- 日志可能输出 API Key、Cookie 或数据库连接串。

启用真实 AI 前还必须确认：

- `TFT_AGENT_CONCLUSION_MODE` 已从 `off` 改为目标模式；
- 模型 Endpoint、Model 和 API Key 已配置在后端；
- 全站、访客和 IP 日额度保持生效；
- Provider 账号侧设置费用/余额告警。

## 7. 建议的初始运行参数

针对 2 核 2GB 单机，压测起点建议保守配置：

```text
Web 实例：1 个常驻
Worker：1 个常驻
Worker concurrency：2
PostgreSQL pool：Web 6、Worker 3
Redis maxmemory：128MB 起步
Redis policy：noeviction
Memory fallback：false
```

原因：当前每进程连接池上限是 10。若以后启动 2 个 Web 加 1 个 Worker，理论上可能占用 30 个数据库连接，对 2GB 单机没有必要。应通过 Compose 为 Web 和 Worker分别覆盖连接池上限。

第二个 Web 实例用于专门的多实例验收，只有内存压力测试通过后才决定是否常驻。对于 100 人在线、个位数平均 RPS，单 Web 实例并不是架构缺陷；共享 PostgreSQL/Redis 已保证以后可横向扩容。

## 8. 测试任务

### WEB-CAP-01：服务器部署预检

目标：确认本地验收过的阶段 0～4 已真实部署到服务器。

步骤：

1. 记录系统、Docker、内存、磁盘和容器版本。
2. 检查 `/api/health`、`/api/ready` 和依赖状态。
3. 检查数据库迁移版本。
4. 检查 PostgreSQL/Redis 没有公网端口。
5. 记录空闲 10 分钟的容器资源基线。

通过标准：所有服务健康，无待执行迁移，无 OOM/重启循环，空闲时至少保留 400MB `MemAvailable`。

### WEB-CAP-02：静态资源冷启动

目标：确认 30 Mbps 带宽下的新用户首次打开体验。

场景：

1. 1 个用户无浏览器缓存打开首页。
2. 20 个用户在 10 秒内无缓存打开首页。
3. 100 个用户在 60 秒内无缓存打开首页。
4. 重复以上场景，但允许浏览器缓存命中。

采集：HTML、JS、CSS、默认背景图的响应大小、下载时间、缓存头、带宽峰值和失败率。

当前实现基线：

```text
默认背景：约 374KB WebP
亚索背景：约 206KB WebP
四张选择器缩略图：合计约 90KB WebP
原始 PNG/JPG：继续保存在仓库作为母版，不是默认网络载荷
壁纸缓存：Cache-Control: public, max-age=31536000, immutable
```

通过标准：

- HTML/JS/CSS 成功率至少 99%。
- 缓存命中后不重复下载未变化的大图。
- 持续公网出口不超过 24 Mbps（带宽上限的 80%）或出现明显排队。
- 100 人冷启动场景首页可交互 P95 不超过 5 秒。

如果优化后仍失败，先继续处理静态资源，而不是增加数据库容量：

- 背景图转换为更小的 WebP/AVIF；
- 为带指纹的静态资源设置长期缓存；
- 大图延迟加载；
- 使用对象存储/CDN 承担静态资源。

### WEB-CAP-03：缓存命中 API 稳态

目标：验证最常见的 100 人在线场景。

负载：100 个虚拟用户、15～30 秒思考时间、持续 15 分钟，主要请求使用已预热查询。

通过标准：

- HTTP 成功率至少 99%。
- 应用自身 5xx 低于 0.5%。
- 缓存命中 API 的 P95 不超过 500ms，P99 不超过 1 秒。
- 服务器 CPU 1 分钟平均低于 70%。
- `MemAvailable` 持续高于 300MB，无 OOM、无持续 Swap in/out。
- PostgreSQL 连接池无持续等待。
- Redis 无拒绝写入、无意外淘汰。

### WEB-CAP-04：100 客户端短时突发

目标：验证短时间集中访问不会拖垮进程。

负载：100 个客户端在 10 秒内各发起一次缓存命中查询。

通过标准：

- 成功率至少 99%。
- P95 不超过 2 秒。
- 峰值 CPU 可以短时接近 90%，但 1 分钟内恢复。
- 突发结束后 readiness 保持正常，队列和连接池在 60 秒内回落。

### WEB-CAP-05：冷缓存与 MetaTFT 隔离

目标：验证外部 Provider 变慢时不会拖垮 Web。

负载：最多 20 个并发冷查询，使用受控查询集合；不得对第三方接口发起无上限随机请求。

通过标准：

- 相同缓存键的并发刷新尽量合并，不形成请求风暴。
- 外部超时按照现有超时预算结束。
- Provider 失败返回明确降级结果，不产生未捕获 5xx。
- 冷查询期间缓存命中请求的 P95 不恶化超过 50%。
- 不出现静默切换到另一个数据来源。

### WEB-CAP-06：PostgreSQL 写入与幂等

目标：验证反馈、事件和审计写入在并发下保持正确。

场景：

- 20 个客户端并发提交不同反馈 ID。
- 20 个客户端并发提交同一个反馈 ID。
- 查询事件写入同时进行反馈关联。

通过标准：

- 不同反馈全部按预期写入。
- 同一反馈 ID 只有一条事实记录。
- 无死锁、外键错误或连接池耗尽。
- 写入 P95 不超过 500ms。

### WEB-CAP-07：Redis 会话、限流和额度

目标：验证 100 人共享 Redis 时的状态一致性。

场景：

- 创建 100 个独立访客会话并执行多轮查询。
- 并发触发同一 IP 的分钟限流。
- 模拟 10～100 个访客共享同一 NAT 出口，记录正常操作被 429 拒绝的比例。
- 并发争用访客、IP 和全站 AI 日额度。

通过标准：

- 会话之间没有数据串读。
- 限流计数不因多个连接而丢失更新。
- 容量压测中的 429 与主动限流分开统计，不能把主动限流误报为服务器错误。
- 全站额度到 50 后不再放行真实 AI，基础查询仍可用。
- Redis Key 均有预期 TTL，Key 中没有原始 IP、Cookie 或用户输入。

### WEB-CAP-08：AI 队列容量

目标：验证全站每日 50 次 AI 的排队能力，而不消耗 50 次真实模型调用。

方法：使用测试 Provider 模拟 5～10 秒响应，在测试命名空间排入 50 个任务；真实 DeepSeek 只做少量端到端冒烟。

通过标准：

- Web 入队 P95 不超过 300ms。
- Worker 并发始终不超过 2。
- Web 普通查询 P95 相比无 AI 负载时恶化不超过 20%。
- 任务没有丢失或重复生成最终查询事件。
- Worker 重启后处理中任务可以恢复或按上限重试。
- 50 个模拟任务最终全部进入 `complete`、受控 `fallback` 或明确 `failed`，没有永久 `running`。

真实模型测试只验证：鉴权、模型名、超时、结果校验、额度扣减和敏感日志。不要用真实 Provider 做容量压测。

### WEB-CAP-09：故障恢复

目标：验证共享存储确实消除了进程内关键状态。

场景：

1. AI 任务运行时重启 Web。
2. AI 任务运行时重启 Worker。
3. 短暂断开 Redis。
4. 短暂断开 PostgreSQL。
5. 恢复依赖并检查 readiness。

通过标准：

- Web 重启不丢已入队任务。
- Worker 重启后任务可恢复且不超过重试次数。
- Redis 不可用时 AI 和配额 fail closed。
- PostgreSQL 不可用时 readiness 失败，不写入本机内存假成功。
- 依赖恢复后服务无需清空业务数据即可恢复。

### WEB-CAP-10：两实例 HTTP 验收

目标：补足当前 Redis 双客户端冒烟没有覆盖的真实 HTTP 负载均衡。

步骤：临时运行 2 个 Web 容器，在每个实例日志中记录脱敏的 `instance_id`，通过 Caddy 连续发起请求。

通过标准：

- 请求实际到达两个 Web 实例。
- 跨实例会话、任务状态和额度保持一致。
- 停止其中一个 Web 后，剩余实例继续提供服务。
- Caddy 不持续把请求发给已经停止的实例。

如果当前 `reverse_proxy app:17317` 无法稳定发现 Compose 扩容后的多个实例，应显式配置可发现的上游或使用外部负载均衡，不能只以 Redis 双客户端测试代替 HTTP 多实例测试。

### WEB-CAP-11：2 小时稳定性测试

目标：发现连接泄漏、内存增长、Redis Key 泄漏和队列积压。

负载：100 个虚拟用户，采用正常在线模型持续 2 小时，AI 使用模拟 Provider。

通过标准：

- 无容器重启、OOM、未处理 Promise rejection。
- 后一小时内存基线相较前一小时增长不超过 10%，或能说明是有上限的缓存预热。
- PostgreSQL 连接数回落，Redis 过期 Key 正常减少。
- 队列等待时间不持续上升。
- 磁盘、日志和网络流量增长符合预期。

## 9. 总体上线判定

必须同时满足：

```text
WEB-CAP-01 通过
WEB-CAP-02 通过或已把大静态资源迁到缓存/CDN
WEB-CAP-03 通过
WEB-CAP-04 通过
WEB-CAP-05 通过
WEB-CAP-06 通过
WEB-CAP-07 通过
WEB-CAP-08 通过
WEB-CAP-09 通过
WEB-CAP-11 通过
```

`WEB-CAP-10` 是宣称“真实 Web 多实例容错”前的必要条件。如果首发只运行一个 Web，它不阻止单实例上线，但对外只能声明“架构支持扩展”，不能声明“已经验证双实例自动切换”。

## 10. 资源升级触发条件

出现任一情况时，不继续提高并发，应升级服务器或拆分托管服务：

- 稳态 `MemAvailable` 低于 300MB；
- 发生 OOM 或持续 Swap；
- PostgreSQL/Redis 与 Web 争抢内存导致延迟明显抖动；
- 稳态 CPU 持续超过 70%；
- 30 Mbps 带宽持续超过 80%；
- PostgreSQL 磁盘或连接池持续等待；
- Redis 达到内存上限或出现写入失败；
- AI 队列等待时间持续增长；
- 系统盘使用超过 70% 且没有可执行的清理/归档方案。

优先级建议：

1. 先压缩/缓存静态资源，避免用服务器升级解决大图下载问题。
2. 内存不足时优先增加内存或拆分 PostgreSQL/Redis。
3. CPU 持续不足时再增加 Web/Worker 实例和 CPU。
4. 只有数据库实测出现瓶颈时才调整连接池和数据库参数。
