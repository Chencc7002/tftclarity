> 目标阈值：成功率至少 99%，静态冷启动请求 P95 小于 5 秒，缓存命中 API P95 小于 500ms

## 结论

- 已证明通过的静态冷启动上限是：100 个用户在 60 秒内打开首页。
- 115 个用户开始超过验收阈值，因此本轮得到的静态冷启动边界是 100～115 用户。
- 主要瓶颈是 30Mbps 公网带宽，不是 CPU 或内存。
- 已证明通过的缓存命中 API 稳态上限是 90 个用户，使用 15～30 秒阅读间隔时 262/262 请求成功，P95 407ms、P99 658ms。
- 100 用户稳态 296/296 请求成功，但 P95 509ms、P99 1.46s，超过既定延迟阈值，因此本轮 API 安全边界是 90～100 用户。
- 100 用户同时发起首个请求的突发场景 P95 2.98s，并出现 4.57% 连接超时，不通过突发验收。
- 测试中发现生产 app 容器原先没有设置 `TFT_AGENT_TRUST_PROXY`；该配置已补充为 `true` 并重建 app。35 个不同测试 IP 随后全部返回 200，证明限流已按客户端 IP 拆分。

## API 结果

结构化快捷查询经过预热后，单用户缓存命中请求 P95 为 201ms，5/5 检查通过，证明查询载荷和 Redis 查询缓存可用。

首次 100 用户测试中，308 个 HTTP 请求只有 60 个被视为成功响应（包含预热请求），248 个返回 `429 rate_limited`。该结果帮助定位到代理信任配置缺失：app 把所有经 Caddy 的用户识别成同一个容器 IP。

由于 app 只在 Docker 内网暴露且公网入口是 Caddy，生产配置已补充：

```dotenv
TFT_AGENT_TRUST_PROXY=true
```

app 重建后已确认容器读取值为 `true`，公网 health/readiness 均返回 200，35 个不同测试 IP 均得到 200 且命中查询缓存。

后续运维仍需确保：

1. Caddy 仍是唯一公网入口，app 的 17317 端口没有映射到公网。
2. 不同客户端 IP 产生不同 Redis 请求限流键。
3. 共享 NAT 场景仍会按同一出口 IP 合并计数，这是预期行为，需要单独评估 30 次/分钟是否过低。
4. 共享 NAT 场景根据实际使用情况调整 30 次/分钟限制，不能通过信任任意公网请求头绕过限流。

修复后的多隧道稳态结果：

| 用户数 | HTTP 请求 | 失败率 | P95 | P99 | 结果 |
| ---: | ---: | ---: | ---: | ---: | --- |
| 80 | 238 | 0% | 364ms | 446ms | 通过 |
| 90 | 262 | 0% | 407ms | 658ms | 通过 |
| 100 | 296 | 0% | 509ms | 1.46s | 延迟阈值失败 |

API 测试通过多条仅本机可访问的 SSH 隧道直达 app，以便为虚拟用户分配独立测试 IP；因此它覆盖 app、Redis 和 PostgreSQL，不包含公网 TLS/Caddy 开销。公网 Caddy 链路已经由静态测试和 health/readiness 冒烟覆盖。
