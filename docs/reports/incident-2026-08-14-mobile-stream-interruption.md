# 2026-08-14 移动端流式查询中断记录

## 现象

- 移动端 Safari 在自然语言查询过程中偶发显示 `Load failed`。
- 失败卡片没有业务错误码，也没有收到 NDJSON 的终止事件。
- 同一设备前一笔查询可以正常完成，因此不是 AI 功能整体不可用。

## 生产证据

排查时间：2026-08-14（Asia/Shanghai）。日志时间以下游服务记录为准。

- 08:50:36 的 `/api/react-chat/stream` 请求成功，HTTP 200，持续约 8.79 秒，完整返回约 110 KB。
- 08:52:40 的同类请求已经由应用返回 HTTP 200 和 NDJSON 响应头，但连接约 6 ms 后中断，只传输了约 520 字节。
- Caddy 记录 `aborting with incomplete response`，并报告上游连接已被关闭。
- 应用、Caddy、Embedding、PostgreSQL、Redis 容器均没有重启，`OOMKilled=false`。
- 同一时间窗口没有内核 OOM、Docker 重启事件或应用级模型拒绝记录。

为保护用户隐私，本记录不保存客户端 IP、Cookie 或完整请求正文。

## 结论

这是一次已经开始返回流式数据、但在终止事件到达浏览器前发生的传输中断。现有证据排除了服务崩溃、内存溢出、部署重启和证据校验失败。最符合证据的原因是移动网络或 Safari 连接在流式传输早期被取消/重置；Caddy 随后关闭了到应用容器的上游连接。

## 修复

1. 前端只对网络异常或“流结束但缺少终止事件”自动续试一次。
2. 用户主动停止、HTTP/业务错误、模型拒绝和证据校验失败不会触发续试。
3. 续试沿用同一个请求 ID、会话和对话气泡，并在 Agent 时间线显示“正在自动恢复本次查询”。
4. 后端仅允许已经断开的原请求复用一次 AI 配额预留；请求正文、用户身份或请求 ID 不一致时必须重新计费。
5. 第二次仍然断流时，保留本地化错误提示和手动重试入口。

## 验证标准

- 第一次流式传输断开后，浏览器自动发起一次续试并能正常渲染最终结果。
- 同一断流请求的两次传输只扣减一次用户 AI 配额。
- 用户点击停止不会自动续试。
- 业务错误不会被误判为网络问题。
- 自动续试失败后不循环重试。

## 发布状态

当前修复仅在本地实现和验证，未部署生产环境。
