# TFTAgent 自然语言智能化持续开发总方案

> 用途：将本文直接交给开发 Agent。开发 Agent 应按阶段连续执行，每个阶段都必须通过验收门后再进入下一阶段。
> 目标：一次确定最终架构，渐进替换当前固定意图路由，最终形成“领域内高覆盖、受控执行、可评估、可持续学习”的 TFT Agent。

## 1. 最终目标与边界

最终目标不是让系统对任何问题都编造答案，而是做到：

1. 对绝大多数 TFT 自然语言问题，能够理解用户想完成的任务。
2. 对现有数据和工具能够支持的问题，生成可执行计划并可靠回答。
3. 对信息不足的问题，只追问一个真正影响结果的关键问题。
4. 对当前能力不支持的问题，准确说明已经理解的需求和缺失能力。
5. 新增工具后，理解层能够通过能力描述自动覆盖更多表达，而不是继续堆叠大量意图分支。
6. 所有模型输出、工具调用和最终结论均可追踪、可取消、受预算限制、可离线评估。

目标范围是 TFT 游戏领域，不承诺成为通用聊天机器人。

建议最终指标：

- TFT 领域识别率不低于 98%。
- 核心动作识别准确率不低于 95%。
- 当前版本核心实体 Top-1 解析准确率不低于 97%。
- 工具路由准确率不低于 95%。
- 有能力支持的问题端到端有效回答率不低于 90%。
- 无能力或证据不足的问题，诚实降级率不低于 98%。
- 不得因为模型规划生成任意 SQL、任意网络请求或未注册工具调用。

## 2. 核心设计原则

### 2.1 语义开放，执行封闭

LLM 可以组合式理解用户动作、对象、条件和目标，但只能调用工具注册表中存在的工具，参数必须通过 Schema 校验。

### 2.2 理解成功不等于回答成功

系统必须区分：

- `understood_and_supported`
- `understood_but_missing_context`
- `understood_but_unsupported`
- `ambiguous`
- `out_of_domain`

不允许将“当前没有工具”误报为“无法理解用户”。

### 2.3 不用新意图枚举修复每个新问法

禁止为了单个失败语句不断增加：

- 一次性 `if/else`
- 仅匹配完整句子的正则
- 高度重叠的新意图名称
- 没有进入评估集的特殊分支

允许增加可复用的领域别名、概念、动作模式、实体类型和工具能力。

### 2.4 保留确定性业务核心

现有数据查询、统计、排序、版本过滤、证据生成、结论校验和安全降级继续由确定性代码完成。LLM 不计算胜率，不直接访问数据库，不决定不存在的实体。

### 2.5 先影子运行，再逐步接管

新理解链路不得直接替换旧链路。迁移顺序必须是：

```text
离线评估
→ 影子解析
→ 记录新旧差异
→ 小流量接管
→ 按动作逐类接管
→ 旧路由成为降级路径
```

### 2.6 上下文按需披露，动态状态放在末尾

系统提示词、核心工具索引和固定规则保持稳定前缀；版本、时间、用户状态、检索证据和运行进度作为动态消息追加到末尾。不得为了让模型“看到最新状态”而每次重写系统提示词。

上下文使用渐进式披露：

```text
固定核心规则
→ 当前任务相关的能力摘要
→ 按需加载完整工具 Schema / 领域说明
→ 动态证据
→ Agent 状态栏
```

当轨迹增长时，保留用户目标、未完成事项、关键工具结果、证据来源和失败原因，将大段原始工具输出压缩为结构化摘要。不能使用简单滑动窗口直接丢弃早期关键结果。

## 3. 目标架构

```text
User Input
  → PreNormalizer
  → Domain Gate
  → Semantic Task Parser
  → TaskFrame
  → Entity / Concept Resolver
  → Context Resolver
  → Ambiguity Policy
  → Capability Matcher
  → Bounded Task Planner
  → Agent Runtime
  → Tool Registry / Tool Executor
  → Evidence Assembler
  → Evidence-backed Conclusion
  → Validation / Correction / Fallback
  → Trace + Evaluation + Failure Mining
```

## 4. 统一语义协议 TaskFrame

固定意图只能作为兼容字段，新的主协议使用组合式任务语义：

```json
{
  "schemaVersion": "task-frame.v1",
  "domain": "tft",
  "action": "compare",
  "subjects": [
    {
      "rawText": "霞",
      "expectedType": "champion",
      "resolvedId": null,
      "confidence": null
    }
  ],
  "candidates": [
    {
      "rawText": "炼刀",
      "expectedType": "item",
      "resolvedId": null,
      "confidence": null
    },
    {
      "rawText": "巨九",
      "expectedType": "item",
      "resolvedId": null,
      "confidence": null
    }
  ],
  "concepts": [],
  "constraints": {
    "patch": "current"
  },
  "goal": "choose_best",
  "expectedOutput": [
    "recommendation",
    "comparison",
    "evidence"
  ],
  "contextReferences": [],
  "ambiguities": [],
  "assumptions": [],
  "confidence": 0.94
}
```

首批稳定动作：

- `search`
- `recommend`
- `compare`
- `rank`
- `explain`
- `analyze`
- `summarize`
- `find_video`
- `unknown`

首批稳定实体类型：

- `champion`
- `item`
- `trait`
- `composition`
- `augment`
- `patch`
- `game_concept`
- `video`
- `player_context`

动作和实体类型应保持少而稳定，通过组合产生能力，不为每个业务组合创建新意图。

`action` 只是粗粒度路由提示，不能成为新的固定意图天花板。Capability Matcher 还必须使用 `userGoal`、实体组合、约束、期望输出和工具能力进行匹配；即使 `action=unknown`，只要用户目标已经被自然语言字段准确表达，也应判定为“理解成功、暂时没有结构化动作或执行能力”，而不是直接拒绝。

## 5. 工具能力协议

工具注册项不仅保存执行函数，还必须声明能力：

```json
{
  "name": "item.compare_for_champion",
  "version": "1",
  "description": "比较指定英雄使用多个装备时的当前版本表现",
  "capabilities": [
    {
      "action": "compare",
      "subjectTypes": ["champion"],
      "candidateTypes": ["item"]
    }
  ],
  "inputSchema": {},
  "outputSchema": {},
  "timeoutMs": 5000,
  "risk": "read_only",
  "trustTier": "first_party",
  "sideEffect": "none",
  "requiresApproval": false,
  "cachePolicy": {},
  "evidenceType": "item_comparison"
}
```

Capability Matcher 根据 TaskFrame 与工具能力匹配，不允许仅靠工具名称字符串猜测。

工具优先设计为少量可组合的领域原语，并只为高频、需要确定性统计或安全封装的任务提供复合工具。不得为每一种用户措辞创建一个工具。

工具执行必须具备：

- 输入输出 Schema 校验
- 超时
- 取消信号
- 最大并发数
- 错误分类
- 可观测事件
- 重试策略
- 幂等性说明
- 缓存策略
- 来源和版本信息
- 来源信任等级
- 是否有副作用
- 所需权限和凭据范围
- 是否需要独立审查或用户确认

工具描述、第三方工具返回值和外部内容都属于不可信数据。运行时必须把“工具说明”“用户指令”“工具结果”按来源和角色隔离，第三方内容不能直接升级为系统指令。

## 6. 受控任务规划

第一版 Planner 只允许生成 1～3 步的 DAG 或顺序计划：

```json
{
  "planVersion": "task-plan.v1",
  "steps": [
    {
      "id": "resolve_champion",
      "tool": "champion.resolve",
      "arguments": {
        "name": "霞"
      }
    },
    {
      "id": "resolve_items",
      "tool": "item.resolve_batch",
      "arguments": {
        "names": ["炼刀", "巨九"]
      }
    },
    {
      "id": "compare_items",
      "tool": "item.compare_for_champion",
      "dependsOn": ["resolve_champion", "resolve_items"],
      "argumentsFrom": ["resolve_champion", "resolve_items"]
    }
  ]
}
```

第一版严格禁止：

- 无限 ReAct 循环
- 模型自行发起任意 HTTP 请求
- 模型生成并执行 SQL
- 运行时安装依赖
- 未经注册的工具调用
- 自动写入长期记忆
- 自动修改业务统计规则
- 多 Agent 自由协作

## 7. 连续实施阶段

### 阶段 0：冻结基线与失败样本

任务：

1. 检查工作区未提交变更，不覆盖、不重置、不混入当前结论层开发。
2. 运行现有全量测试并保存基线。
3. 从真实使用记录中提取失败问法，做隐私清理。
4. 建立首批至少 300 条自然语言评估数据。
5. 为每条数据标注领域、动作、实体、约束、是否可支持、期望降级行为。

首批必须包含：

- 玩家简称和黑话
- 错别字、同音词、口语
- 多轮省略
- 比较、推荐、解释、排行
- 多条件组合
- 模糊概念，例如“九五”
- 装备二选一，例如“霞的炼刀和巨九选哪个”
- 当前版本和历史版本
- 视频搜索
- 超出领域的问题
- 数据不足或工具不支持的问题

验收门：

- 原有测试保持通过。
- 数据集可重复运行。
- 每个失败类别至少有一个独立标签。
- 不能只使用开发者编写的标准句。
- 300 条只是启动集；在对外声称达到 95% 以上覆盖率前，必须扩展到至少 1000 条真实风格样本，并保留按时间或来源隔离、从未参与提示示例和开发调试的独立测试集。

### 阶段 1：Agent Runtime、工具注册和最小评估层

执行现有文档：

`docs/next-stage-agent-runtime-tools-evaluation-prompt.md`

本阶段仍运行固定流程，不引入自主规划。

验收门：

- 现有生产链路行为兼容。
- 每次请求拥有 runId、状态、预算、取消、超时和完整事件。
- 当前结构化查询能力已包装为注册工具。
- 离线评估能够输出 JSON 和 Markdown 报告。

### 阶段 2：TaskFrame 与影子语义解析

任务：

1. 实现 `task-frame.v1` Schema、校验器和版本迁移策略。
2. 实现 Semantic Task Parser。
3. 解析器输出动作、对象、候选项、条件、目标、歧义、置信度。
4. 旧 IntentEnvelope 保留。
5. 在线请求同时运行旧解析和新解析，但仍由旧解析执行。
6. 记录新旧解析差异，不记录敏感原文。
7. 建立可检索的少样本示例库，每次只注入最相关的少量示例。
8. 固定系统提示词和核心工具索引的顺序，动态版本、时间和用户状态追加到上下文末尾。
9. 为每轮规划生成结构化状态栏：目标、已完成步骤、剩余预算、未解决歧义和关键证据。
10. 定义上下文压缩触发条件和保留字段，不采用简单滑动窗口删除历史。

验收门：

- 动作识别准确率不低于 92%。
- 领域识别率不低于 97%。
- 不支持能力不再被误报为无法理解。
- 新链路影子运行不改变用户可见结果。
- 单次解析 Token 和延迟有明确预算。
- 可观测数据能够区分缓存输入、未缓存输入和输出 Token。
- 压缩前后的任务目标、关键证据和工具完成状态保持一致。

### 阶段 3：实体与游戏概念链接

任务：

1. 复用现有别名、拼音、模糊匹配、语义候选和当前版本目录。
2. 将实体解析从意图解析中彻底分离。
3. 每个实体输出原文、规范 ID、类型、版本、候选项、来源和置信度。
4. 增加 `game_concept`，支持“九五”“赌狗”“运营”“连败”“前排装”等非官方实体。
5. 解析顺序保持：

```text
exact
→ normalized alias
→ current-patch catalog
→ pinyin/fuzzy
→ semantic retrieval
→ LLM candidate rerank
```

6. 不确定时保留多个候选，不得强行塞进错误实体类型。

验收门：

- 当前版本核心实体 Top-1 准确率不低于 97%。
- 玩家黑话和别名 Top-3 召回率不低于 98%。
- 不存在实体的误命中率低于 2%。
- “九五”和装备简称进入可复用的概念/别名体系，而不是句子级规则。

### 阶段 4：上下文解析与智能追问

任务：

1. 支持“这两个”“那巨九呢”“还是刚才那套”等上下文引用。
2. 区分用户明确条件、会话继承条件和系统默认条件。
3. 建立 Clarification Policy。
4. 只有当歧义会显著改变工具选择或结论时才追问。
5. 优先顺序：

```text
上下文解决
→ 候选并行检索
→ 带明确假设回答
→ 追问一个关键问题
```

验收门：

- 多轮引用解析准确率不低于 90%。
- 不必要追问率低于 5%。
- 必要追问不得提供与问题无关的固定按钮。
- 无法回答时能够复述已经理解的用户目标和缺失信息。

### 阶段 5：能力匹配与受控 Planner

任务：

1. 工具注册项增加可机器匹配的 capabilities。
2. 实现确定性优先的 Capability Matcher。
3. 单工具可完成时，不调用 LLM Planner。
4. 组合任务才调用 Planner。
5. Planner 只生成注册工具组成的 1～3 步计划。
6. 计划必须通过 Schema、依赖关系、预算和权限校验。
7. 无匹配工具时返回 `understood_but_unsupported`。
8. 工具少于约 30 个时使用稳定、分组的能力目录；工具规模明显增长后才启用分层索引和主动工具发现。
9. Planner 默认只能选择第一方只读工具；有副作用、第三方凭据或外部通信的工具必须经过独立策略检查。
10. 重试有副作用的工具前必须验证幂等键或确认前一次未成功。

首批端到端能力：

- 英雄装备推荐
- 英雄装备比较
- 阵容排行
- 阵容趋势
- 阵容推荐
- 游戏概念到阵容的语义检索
- 版本说明
- 现有问答能力的组合调用

验收门：

- 工具选择准确率不低于 95%。
- 单工具问题没有无意义的多步规划。
- 最大步骤、工具调用次数和 Token 预算始终生效。
- 工具失败不会让 Agent 陷入循环。
- 不可信工具描述和工具结果不能改变系统权限或绕过计划校验。

### 阶段 6：新链路逐步接管

按动作逐类切换：

1. `search`
2. `rank`
3. `recommend`
4. `compare`
5. `explain`
6. `analyze`

每一类都执行：

```text
离线通过
→ 影子差异通过
→ 小流量
→ 观察错误率和降级率
→ 扩大流量
→ 旧路由保留为 fallback
```

验收门：

- 有能力支持的问题有效回答率不低于 90%。
- 旧链路核心回归用例全部通过。
- 错误工具调用率低于 1%。
- 线上失败可通过 run trace 定位到解析、实体、规划、工具或结论层。
- 核心回归用例至少重复运行 3～5 次，同时报告 Pass@k 与 Pass^k，不能用“多次中偶尔成功”掩盖不稳定。
- 评估报告按动作、实体类型、口语/错别字/上下文、版本和工具类型切片，并同时报告质量、延迟和 Token 成本分布。

### 阶段 6.6：架构收敛

阶段 6.6 是阶段 6 与阶段 7 之间的正式发布门，不增加用户能力。它负责把阶段 6 已验证的语义链从“授权旧链执行”收敛为真正的生产主链：

`TaskFrame → Capability Matcher → ExecutionPlan → ExecutionPlanExecutor → Tool Registry / ToolExecutor → Evidence Validator → 回答 / 追问 / 降级`

硬性要求：

- 单工具 Fast Path 不调用 LLM Planner，但必须生成单步 `ExecutionPlan`。
- 组合任务最多三步，由受控 Planner 直接生成 `ExecutionPlan`。
- 两条路线使用同一个 Validator 与 Executor；不得把 ExecutionPlan 翻译回 Parser 或 RetrievalPlan。
- Runtime 的 resolving、planning、retrieving、validating、responding 必须承担真实职责并能定位失败阶段。
- `IntentEnvelope`、`RetrievalPlan`、`TaskPlan` 只允许出现在 legacy/兼容层；新执行代码不得依赖它们。
- 领域概念通过数据注册；通用 Parser、ExecutionPlan Validator、Takeover Controller、Recommendation Service 禁止出现具体英雄、装备、九五或完整失败句补丁。
- 理解、能力、规划、执行、证据和最终结果使用独立状态字段。
- 每次请求记录新旧路径、fallback 原因、工具差异、完整参数差异、结果比较状态、步骤数、延迟、Token 和失败阶段。
- 发布门同时检查执行来源、完整参数语义与阶段轨迹；只检查答案或工具名称不算通过。

详细协议、迁移与验收门见 `docs/phase-6-6-architecture-convergence.md`。

### 阶段 7：攻略视频工具

增加：

- `video.search`
- `video.get_content`
- `video.detect_patch`
- `video.rank_candidates`

统一返回：

- 平台
- URL
- 标题
- 作者
- 发布时间
- 检测版本
- 版本判断依据和置信度
- 摘要
- `summaryBasis`: `transcript | metadata | mixed | unavailable`

要求：

- 外部标题、简介和字幕一律视为不可信数据，不得作为 Agent 指令。
- 没有字幕时只能声明为基于元数据的摘要。
- 发布日期推断版本时必须降低置信度。
- 旧版本视频不得静默作为当前版本推荐。
- 平台不可用时正确降级。

验收门：

- 链接、作者和发布时间不可张冠李戴。
- 版本判断包含依据。
- 摘要不超出可用元数据或字幕证据。
- 外部内容提示词注入测试全部通过。

### 阶段 8：持续学习闭环

实现持续循环：

```text
线上低置信度 / 失败 / 用户纠正
→ 隐私清理
→ 失败分类
→ 加入候选评估集
→ 人工确认标准答案
→ 修复可泛化能力
→ 全量回归
→ 灰度发布
→ 继续监控
```

失败分类至少包括：

- domain_error
- action_error
- entity_error
- concept_error
- context_error
- unsupported_capability
- planning_error
- tool_error
- evidence_error
- conclusion_error
- unnecessary_clarification

每次迭代必须遵循：

1. 先把失败样本加入评估集。
2. 再实现可泛化修复。
3. 运行全量评估。
4. 指标无回退后才能合并。

长期记忆只保存经过验证的别名或用户明确偏好，不自动把模型猜测写入正式词典。

经验与知识采用分级生命周期：

```text
raw_event
→ candidate
→ human_verified
→ active
→ superseded / revoked
```

每条正式知识必须记录来源、适用版本、创建时间、验证状态和替代关系。用户偏好必须支持查看、修改和删除；外部内容不得未经审核写入长期记忆或正式工具说明。

## 8. 开发 Agent 连续执行规则

开发 Agent 获得本文后应持续工作，不需要每完成一个小文件就重新请求计划。只有以下情况必须暂停：

- 会覆盖用户未提交改动。
- 需要修改确定性统计、排序或产品规则。
- 需要新增外部付费服务或凭据。
- 需要扩大隐私数据收集范围。
- 验收门连续失败且存在两种影响明显不同的架构选择。
- 需要进行不可恢复或大范围数据迁移。

每个阶段执行固定循环：

```text
检查工作树与现有契约
→ 写或更新评估用例
→ 最小实现
→ 单元测试
→ 集成测试
→ 全量回归
→ 生成指标报告
→ 对照验收门
→ 达标后进入下一阶段
```

每阶段使用独立提交，禁止把无关工作混入同一提交。已有未提交文件默认属于用户。

## 9. 观测指标

每个请求至少记录：

- runId
- TaskFrame schema 版本
- 识别动作和置信度
- 实体解析结果和来源
- 是否使用上下文或默认值
- 匹配到的能力
- 计划步骤
- 工具耗时和错误类型
- 输入、缓存输入和输出 Token
- 是否追问
- 是否降级
- 最终证据类型
- 总耗时

日志默认不保存密钥、完整外部字幕和不必要的用户原文。

### 9.1 真实 LLM 测试分层

真实 LLM 测试是发布门的一部分，但不得混入默认单元测试，也不得让每次本地修改都产生外部费用。

测试分为四层：

| 层级 | 是否调用真实 LLM | 运行时机 | 目的 |
|---|---|---|---|
| T0 单元与契约测试 | 否 | 每次修改 | 验证 Schema、状态机、预算、工具参数、验证器和降级逻辑 |
| T1 Provider 适配测试 | 否，使用固定 fixture / fake provider | 每次提交或 PR | 验证请求格式、错误分类、重试、usage 解析和响应兼容 |
| T2 真实 LLM 冒烟 | 是 | Parser、Prompt、模型、Provider 或工具描述发生变化后 | 用 20～50 条代表性用例验证真实结构化输出和基础理解 |
| T3 发布候选评估 | 是 | 阶段验收和发布前 | 对分层抽样的 100～300 条用例重复运行 3～5 次，评估 Pass@k、Pass^k、成本和延迟 |
| T4 影子流量 | 是，复用真实请求但不影响用户结果 | 新链路接管前 | 比较新旧解析、工具选择和降级行为 |

至少每个版本周期对完整独立测试集运行一次真实 LLM 评估；日常开发可使用分层抽样，避免每次对 1000 条数据重复产生费用。

真实调用必须记录：

- Provider 和模型标识
- Prompt / TaskFrame / Tool Registry 版本
- 测试数据集版本
- temperature 等推理参数
- 输入、缓存输入和输出 Token
- 首 Token 和总延迟
- 原始结构化输出或经过脱敏的失败片段
- 重试次数和错误类型

真实调用必须具备：

- 独立命令，例如 `npm run eval:llm:live`
- 显式的 live 开关，默认 `npm test` 不访问外部模型
- 请求数、Token、费用和墙钟时间预算
- 超过预算立即停止
- API Key 只从环境变量读取
- Provider 不可用时报告为外部依赖失败，不伪装成业务逻辑通过

发布门不能只依赖 Mock 测试；但真实 LLM 结果也不能替代确定性单元测试。两者必须同时通过。

## 10. 预期效果

### 完成阶段 1 后

- 架构具备统一运行状态、工具注册、预算、取消和评估底座。
- 用户可见理解能力基本不变。
- 后续增加理解能力不再继续散落到服务器和服务层。

### 完成阶段 2～3 后

- 系统能够识别更多口语、别名、黑话和新组合表达。
- “九五”不再被当成不存在的固定阵容筛选字段。
- “霞的炼刀和巨九选哪个”能够解析为英雄条件下的装备比较。
- 即使缺少工具，也能够说明已经理解的问题。
- 预计 TFT 单轮问题理解覆盖率可达到 90%～95%。

### 完成阶段 4～6 后

- 支持“这两个哪个好”“那巨九呢”等上下文省略。
- 新问题主要通过动作、实体、条件和工具能力组合完成，不再依赖新增固定意图。
- 支持 1～3 步的受控组合查询。
- 预计 TFT 领域理解覆盖率达到 95%～98%。
- 对已有数据能力覆盖的问题，有效回答率预计达到 85%～92%。
- 失败时能够明确区分不理解、缺上下文、缺数据和缺工具。

### 完成阶段 7 后

- 可以搜索 Bilibili 等平台的攻略候选。
- 返回链接、发布时间、检测版本、判断依据和证据范围内的摘要。
- 能区分字幕摘要和仅元数据摘要。

### 完成阶段 8 后

- 新的真实失败问法可以稳定进入“收集—标注—回归—修复—灰度”的闭环。
- 系统能力会随评估集和工具注册持续扩展，而不是随意堆积特殊规则。

## 11. 工作量与风险预期

基于现有项目已有解析器、实体解析、检索、证据和结论校验基础，整体属于中等偏大的架构升级，不需要推倒重写。

单人连续开发的粗略预期：

- Runtime、工具注册、最小评估：3～6 个工作日。
- TaskFrame、影子解析和实体概念链接：5～10 个工作日。
- 上下文、能力匹配、Planner 和逐步接管：8～15 个工作日。
- 视频工具和持续学习闭环：5～10 个工作日。

总计约 4～8 人周，具体取决于真实评估数据质量、外部视频元数据可用性和线上灰度条件。

主要风险：

- 只改 Prompt，不改固定执行模型，效果很快达到上限。
- 过早让 Planner 自由循环，成本和错误率上升。
- 评估集过于标准化，离线指标很好但真实口语仍失败。
- 实体别名跨版本污染。
- 将“不支持”误当作“不理解”。
- 外部视频字幕携带提示词注入。

## 12. 最终完成定义

同时满足以下条件才算完成：

- 新 TaskFrame 成为主要理解协议。
- 固定 IntentEnvelope 降为兼容或降级协议。
- 工具注册表是系统能力的唯一可信目录。
- Planner 只能生成受预算限制的注册工具计划。
- 截图中的两类问题都有端到端回归测试。
- 至少 300 条真实风格启动集持续运行；宣称 95% 以上覆盖率时，独立测试集所在的总数据规模至少达到 1000 条。
- TFT 领域识别、实体解析、工具路由和端到端指标达到目标。
- 无能力问题可以准确降级，不编造答案。
- 新增视频工具不需要修改核心意图枚举。
- 全量自动化测试通过。
- 文档包含协议、工具开发规范、评估方法、灰度和回滚方式。

## 13. 《深入理解 AI Agent》逐章审计结论

本方案按 `bojieli/ai-agent-book` 第 1～10 章进行审计。结论如下：

| 章节 | 对本项目的判断 | 方案状态 |
|---|---|---|
| 第1章 Agent 基础 | 应从固定工作流演进为 LLM、上下文、工具共同组成的受控 Agent；Harness 继续承担约束、验证和纠正 | 已覆盖 |
| 第2章 上下文工程 | 稳定前缀、渐进式披露、状态栏和轨迹压缩是 Runtime 的必要组成，不应只统计 Token | 本轮补强 |
| 第3章 用户记忆和知识库 | 现有结构化数据、语义检索和轻量偏好方向正确；复杂查询可有限迭代检索，但记忆冲突、来源、版本和删除权需要明确 | 本轮补强 |
| 第4章 工具 | 工具注册、Schema、异步、取消和主动发现方向正确；需补充信任等级、最小权限、独立策略检查和有副作用工具的幂等控制 | 本轮补强 |
| 第5章 Coding Agent | 本项目是封闭垂直领域，不应把任意代码生成作为产品运行时核心；确定性统计代码继续作为受控工具 | 明确不引入 |
| 第6章 Agent 评估 | 持续评估是主线而非附加项；需同时测成功上限、重复稳定性、成本、延迟、检索覆盖和分层失败原因 | 本轮补强 |
| 第7章 模型后训练 | 当前数据量和协议仍在演进，SFT/RL 成本高且可能固化错误；先用 Prompt、RAG、工具和评估解决 | 暂缓 |
| 第8章 Agent 自我进化 | 采用外部化学习，把失败样本沉淀为评估、别名、概念、知识和工具；必须审核、版本化、可撤销 | 已覆盖并补强 |
| 第9章 多模态与实时交互 | 当前视频需求首先是搜索、元数据和字幕工具，不等同于实时视频理解；截图、语音和 GUI 控制留作独立扩展 | 暂不进入主线 |
| 第10章 多 Agent | 当前任务没有单 Agent 无法获得的新信息，多 Agent 只会增加成本；工具执行结果和确定性验证器已经提供有效的新信息反馈 | 明确不引入 |

### 后训练启用门槛

仅当同时满足以下条件才评估 SFT：

- TaskFrame 和工具协议已稳定至少两个版本周期。
- 已有数千条经过人工验证、分布覆盖充分的高质量样本。
- 同一类失败无法通过实体库、检索、提示、工具或 Planner 修复。
- 有独立保留测试集并能证明泛化收益。
- 推理成本或延迟收益足以覆盖训练和维护成本。

RL 不属于当前可预见阶段，除非将来存在高频、可自动验证、长轨迹决策任务，并已经拥有稳定仿真环境和奖励定义。

### 多模态启用门槛

- 视频字幕和元数据无法满足用户对“视频实际内容”的总结要求时，再增加离线抽帧、OCR、ASR 和 VLM 分析工具。
- 用户明确需要语音实时对话时，再建立快慢模型解耦、流式打断和延迟预算。
- 不使用 GUI/Computer Use 代替已有稳定 API；只有平台没有可用接口且合规允许时才评估浏览器操作。

### 多 Agent 启用门槛

只有协作能引入单 Agent 当前拿不到的新信息时才评估多 Agent，例如独立视觉审查、隔离安全审查或大规模并行外部调研。让多个相同模型围绕同一段文本互相讨论，不构成引入多 Agent 的理由。
