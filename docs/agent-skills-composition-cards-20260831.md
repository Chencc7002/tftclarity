## 本轮产品约定

- 装备、阵容成员、来源排序和站位由注册工具提供，模型不能自行生成或改动。
- 推荐多个阵容卡片，每张包含自己的成员、统计与站位；站位不是独立推荐列表。
- Skill 告诉模型调用哪些工具，并通过 Prompt 指导解读已取得的事实。
  不新增“解读工具”，不把建设新的知识管线作为解读的前提。
- 解读可以复用有效工具结果中的机制、属性等事实；缺少因果依据时说明限制，
  不能把统计相关性或模型记忆写成已验证机制。
- 什么时候考虑玩保持一般条件：拿到工具推荐的装备，或者来牌、升星顺。
  不据此声称知道玩家当前局面，不扩展到搜牌、升级或经济决策。

## 实现

`src/skills/definitions/unit-play-guidance.js` 保留 1.2.0 定义，新增 1.3.0：
明确逐卡使用对应的 `tacticalDetailQueryPlan` 取得站位，并在各自卡片中解读。
允许工具、facet、数据依赖及 Evidence / completion policy 没有扩大。
结束观测适配器继续兼容 1.1.0、1.2.0，并识别同契约的 1.3.0。
PR1C / PR1D 冻结定义和实验没有改写。

当前 ReAct 验证器要求先有 `comps_rankings` 的 resolved 结果才能查询战术详情。
因此初始多阵容查询即使返回 unfiltered 结果和逐行计划，也不意味着可以跳过
此门槛。指引要求必要时先通过原工具解析该卡片的确切身份；没有修改验证器。
调用仍服从现有预算、必须执行的后续动作、澄清和结束规则。

展示层新增 `src/app/small-window-ui/composition-card-details.js`，只关联本轮
已有的 Ledger 快照，不检索数据、不新增 Evidence，也不代替服务端验证：

- 必须是引用过的、已验证的 MetaTFT 阵容和战术详情；历史、过期或 stale
  证据不能用于绑定。阵容与战术详情分别按现有 30 分钟、5 分钟窗口检查。
- 检查来源时间、缓存有效期、赛季、provider composition ID、cluster ID，
  以及完整成员集合。显示用的 `cluster:` 标识不能替代 provider ID。
- 检查站位 cell 与行列一致，拒绝重复格子、错误成员或跨阵容结果。
- 保留来源顺序和原始站位；partial 只显示已知部分并提示不完整。
  没有匹配站位时保留阵容卡片，明确提示“暂无可验证的站位数据”。
- 每张快照卡片的详情键包含自身赛季和 Evidence ID。展开不会偷偷再查询
  `/api/comp-details`，从而不会展示模型未取得的另一份站位。

`composition-result-groups.js` 和 `app.js` 把绑定后的站位放回所属卡片。
成功绑定的战术详情不再覆盖整个阵容榜；装备结果也可同时展示多个阵容卡片。
独立战术详情查询保留原视图，原生 Quick Task / 趋势卡片保留既有懒加载路径。
本轮没有改变 Quick Task 路由、工具 schema、权限、统计排序或生产模型输入。
