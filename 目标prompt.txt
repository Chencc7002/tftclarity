你需要在当前 TFTAgent 仓库中完成 ConversationState v2 与 TurnDelta 多轮上下文架构重构。

首先完整阅读开发交接文档：

docs/conversation-state-v2-development-handoff.md

同时阅读文档中“给开发 Agent 的执行指令”列出的现有架构文件。本文档是本次开发的需求、架构边界和验收标准，必须遵守。

核心目标：

把当前依赖关键词、正则和领域专用继承函数的上下文处理方式，重构为统一链路：

当前输入 + ConversationState.v2
→ Turn Interpreter
→ TurnDelta.v1
→ 确定性 Context Reducer
→ Resolved TaskFrame
→ 现有 Phase 6.6 执行链
→ 结果状态回写

需要解决的不只是单句：

“可以多推荐几套吗”

而是整类多轮自然语言操作：

- 继续当前任务
- 请求更多或换一批
- 增加条件
- 删除条件
- 替换条件
- 切换任务
- 返回之前任务
- 补充澄清信息
- 取消任务
- 结果已经耗尽

强制架构要求：

1. 不得通过增加完整句子正则、关键词白名单或针对测试案例写补丁解决。
2. LLM 只负责生成受约束的 TurnDelta，不负责选择最终工具、生成完整工具参数、统计或排序。
3. Context Reducer 必须是确定性纯逻辑，相同 state + delta 得到相同结果。
4. Phase 6.6 的 ExecutionPlan、Runtime、Tool Registry 和 Evidence Validator 保持执行主权。
5. 不重写数据抓取、缓存、排行榜算法和前端。
6. comp、unit 等领域最终不得各自维护独立的上下文继承事实。
7. 迁移期允许 shadow 对比，但切换完成后不能让新旧逻辑同时修改请求。
8. 保留旧 session 的兼容读取和可回滚能力。
9. 不得覆盖或删除用户已有的无关未提交修改。
10. 不要提交或推送 Git，完成后等待我审核。

执行方式：

第一步：基线审计

- 执行 git status --short。
- 执行 npm test，记录基线结果。
- 检查交接文档提到的当前函数和真实调用链。
- 如果文档和代码不一致，以代码事实为准，但必须记录差异。
- 先给出简洁的实施顺序，然后直接开始开发，不要只停留在计划。

第二步：实现协议

实现并测试：

- ConversationState.v2
- TurnDelta.v1
- schema 创建、规范化和校验
- 旧 session value 到 v2 的迁移适配
- conversationId 隔离
- pendingClarification
- lastResult 结构化元数据
- shownIds 上限与结果耗尽状态

第三步：实现理解与合并

- 基于现有结构化语义解析能力实现 Turn Interpreter。
- 输入当前消息和紧凑的活动任务状态。
- 输出严格、可校验的 TurnDelta.v1。
- 实现确定性 Context Reducer。
- 支持 new、continue、modify、switch、return、cancel。
- 支持约束 set、add、remove、replace、clear。
- 非法 delta 必须拒绝或澄清，不能静默猜测。

第四步：接入现有执行链

- 在 TaskFrame 进入 Phase 6.6 执行链之前完成状态合并。
- 现有 Capability Matcher、ExecutionPlanExecutor 和 Tool Registry 不变。
- 从结构化执行结果提取 lastResult，不得从最终文案反向解析。
- 工具失败、澄清或证据不足不能污染上一条成功任务状态。

第五步：迁移

提供：

TFT_AGENT_CONVERSATION_STATE_V2_MODE=off|shadow|on

先完成 shadow 差异记录，再切换新链路。

差异至少记录：

- task relation
- active task
- clarification decision
- tool
- complete parameters
- result state
- exhausted decision

最终生产主路径退出以下旧逻辑的上下文决策权：

- inheritCompRankingFromSession()
- inheritParsedFromSession()
- isCompRankingFollowUp()
- 其他阵容或英雄专用续问判断

不要为了移除而一次性删除仍用于回滚的代码；但必须保证 on 模式下它们不再二次修改请求，并列出最终删除清单。

第六步：测试

至少实现并运行：

- schema 单元测试
- reducer 确定性测试
- session 迁移与会话隔离测试
- 阵容更多结果测试
- 结果耗尽测试
- 条件增加、删除和替换测试
- 英雄/装备多轮继承测试
- 待澄清补充测试
- 任务切换和任务恢复测试
- 工具失败不污染状态测试
- 完整 npm test

必须覆盖这条真实序列：

1. 推荐几个赌狗阵容
2. 可以多推荐几套吗

如果上一轮是 3/3，第二轮应保留阵容任务和赌狗条件，并解释结果已经耗尽；不得询问英雄。

还要覆盖：

- 推荐几个赌狗阵容 → 只看大师以上
- 推荐几个赌狗阵容 → 不要赌狗了
- 推荐几个热门阵容 → 换一批
- 霞带什么装备 → 第二套呢
- 霞带什么装备 → 如果没有轻语呢
- 霞带什么装备 → 换成卡莎
- 两个 conversationId 交错续问

第七步：真实 LLM 评估

完成确定性测试后，使用当前配置的真实 LLM 运行独立改写评估。

要求：

- 每个关键语义至少重复 3 次。
- 记录 provider fallback。
- 不把评估句子复制到生产 prompt 或正则。
- LLM 不可用时，测试受控降级，不得错误调用工具。
- 如果当前环境缺少 API 配置，跳过真实调用但生成可执行的评估命令和明确报告，不能伪造通过。

完成标准：

- npm test 零失败。
- 新增确定性测试全部通过。
- 目标多轮序列全部通过。
- 不出现跨会话状态泄漏。
- on 模式不存在新旧逻辑二次合并。
- 工具选择和完整参数准确率不得低于当前基线。
- 没有针对示例句子的完整句子补丁。
- 通用 Agent 层没有具体英雄、装备或阵容实例分支。
- 真实 LLM 上下文 Pass^3 至少达到交接文档门槛。

完成后向我提交一份开发报告，必须包含：

1. 实际修改文件。
2. 最终架构和数据流。
3. 新旧逻辑迁移情况。
4. 执行过的测试命令与真实结果。
5. 真实 LLM 的 provider、model、运行次数和结果。
6. 未完成项和已知风险。
7. 回滚方式。
8. 建议删除的遗留代码。
9. git status --short 输出。

遇到普通实现问题时自行检查代码、测试并继续推进。只有在需要改变上述架构目标、扩大业务范围或可能破坏现有数据兼容时，才暂停并向我确认。
